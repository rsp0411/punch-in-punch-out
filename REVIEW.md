# REVIEW.md

Defects found in the starter `app/main.py`. "Where" refers to the starter's function names.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Uses the punch-in's own date and (naive, server-local) clock instead of IST, and ignores overnight shifts, so the shift start lands on the wrong day. | Server in UTC: 09:45 IST punch gets compared with a 09:30 *UTC* shift start. Overnight employee punching at 05:50 gets a nonsense value. | Shift start is built from the record's attendance date in IST (`shift_instant`), so overnight shifts work. |
| 2 | `compute_late_minutes` | Floors to whole minutes *before* comparing, with `> 10`. 10:00:30 after start floors to 10, is not `> 10`, so it returns 0, but R2 says anything strictly more than 10:00 is late. | Shift 09:30, punch 09:40:01 expected 10, got 0. | Compare in seconds (`secs > 600`), then floor to minutes. |
| 3 | `compute_late_minutes`, `compute_work_hours`, `punch_in` | Instants are not truncated to whole seconds (R1); the sub-second part leaks into stored values and calculations. | Punch at 09:40:00.900 stored with milliseconds; boundary cases flip. | `ms_to_dt` and `trunc` cut to whole seconds before any calculation or storage. |
| 4 | `compute_work_hours` | Python `round()`: float arithmetic plus banker's rounding, but R4 wants half-up. | 4.495 h or 2.125 h round the wrong way; half_day flips at 4.50. | Integer arithmetic: `floor(secs*100/3600 + 1/2)` in hundredths. |
| 5 | `compute_overtime` | No 30-minute minimum (R3), uses the record date for the shift end so an overnight shift ends a day early, and mixes naive and aware datetimes (can raise `TypeError`). | Punch-out 18:35 returns 5 instead of 0; overnight 06:40 punch-out returns a huge negative-turned-0 or a wrong value. | Shift end built from the attendance date (+1 day if overnight); minutes below 30 become 0. |
| 6 | `punch_in` (timestamps) | `datetime.fromtimestamp(ms / 1000)` is server-local and naive; `.date()` is therefore the server's date, not the IST date (R1). `if body.punched_at` also treats 0 as "not supplied". | Run on a UTC host: a 02:00 IST punch lands on the previous date. | `ms_to_dt` gives UTC-aware datetimes; the date is derived in IST by `attendance_date_for` (with the overnight exception). |
| 7 | `punch_in` (unknown employee) | `emp` is `None` for an unknown `emp_code`, so `emp["shift_start"]` raises `TypeError` and returns 500 instead of 404. | POST with `emp_code: "NOPE"`. | 404 before anything else. |
| 8 | `punch_in` (duplicates) | Check-then-insert race, and there is no unique index, so two simultaneous requests both pass the check and create two records. | Fire two identical requests in parallel; both return 201. | Unique index on `(emp_code, date)` and `insert_one` catching `DuplicateKeyError` -> 409. |
| 9 | `punch_in` (input and output) | `status` is a free string (`ABSENT`, `"banana"` accepted); `punched_at` accepts seconds-looking values, floats and strings; the response leaks the `_id` as `id`; `punch_in` goes out as a datetime object, not epoch ms. | POST `status: "ABSENT"` returns 201. Response contains `id`. | `PresenceStatus` literal, strict bounded `EpochMs` type, `record_out` (no `_id`, epoch ms, defaults for legacy gaps). |
| 10 | `create_employee` | Check-then-insert race with no unique index (duplicate `emp_code`s under concurrency); `created_at` is naive local time and returned as a datetime, not epoch ms; no validation of `emp_code` format, e-mail, `HH:MM` shift times, `joined_on` being a real date, or `shift_start == shift_end`. | Two parallel creates both get 201; `shift_start: "25:99"` is accepted. | Unique index plus `DuplicateKeyError` -> 409; pydantic constraints per the contract; UTC `created_at`, returned in epoch ms. |
| 11 | `list_employees` | `skip = page * page_size` skips the whole first page (should be `(page - 1) * ...`); `total` ignores the department filter; no sort by `emp_code`; `page`/`page_size` unvalidated (0, negative, 10 000). | `?page=1` never shows the first employees; `total` equals the whole collection. | Correct offset, `count_documents(filter)`, `.sort("emp_code")`, `page >= 1`, `1 <= page_size <= 100`. |
| 12 | `list_attendance` | Loads the whole collection into memory (`list(find(q))`), sorts and slices in Python; no tie-break on `emp_code`. Hopeless at 100k records. | 100k documents: seconds per request and large memory use. | Server-side `sort`/`skip`/`limit` with the sort `(date desc, emp_code asc)`, backed by indexes. |
| 13 | `list_attendance` (contract) | Dates and `status` are unvalidated (`date_from=banana` -> silently empty), no `date_from > date_to` 422; output leaks `id` and datetime objects; legacy documents without `half_day` / `history` come out with those keys missing. | `?date_from=2026-13-45`; `GET` on the legacy sample record. | Pattern plus real-date validation, `Status` literal, 422 on inverted range, `record_out` fills defaults. |
| 14 | `health` | Always returns 200 even if MongoDB is down; the contract requires 503. | Stop MongoDB, call `/health`. | Pings MongoDB; any `PyMongoError` -> 503. |
| 15 | module level | No indexes at all, so every filter is a collection scan and uniqueness is unenforced; `MongoClient` is created without `tz_aware=True`, so every datetime read back is naive and silently treated as local time. | `explain` shows `COLLSCAN`; naive datetimes in code. | Idempotent `ensure_indexes()` at startup, `tz_aware=True` client, short server-selection timeout so `/health` answers quickly. |

## Looked at and judged fine

- `load_dotenv()` without `override=True` already lets real environment variables win over `.env`, as required.
- Sync (`def`) endpoints with PyMongo: FastAPI runs them in a thread pool, so blocking calls don't block the event loop, and the client is thread-safe.
- `doc.pop("_id", None)` after `insert_one` in `create_employee` does keep `_id` out of the response (the response shape was the problem, not the leak).
